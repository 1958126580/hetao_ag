Hetao Smart Agriculture & Animal Husbandry
Library Design ( hetao_ag )
Modular Architecture Overview
The hetao_ag  library is organized as a collection of cohesive Python packages, each targeting a critical
domain of smart agriculture and animal husbandry. The architecture emphasizes  modularity, allowing
experts to use or extend specific components as needed. All code and documentation are in English,
following PEP 8 and international conventions for clarity and global collaboration. The design prioritizes
international standards – e.g., using SI units, established scientific models, and open data formats – to
ensure consistency and trustworthiness across academic and field deployments.

├── water/         # Water cycle modeling: evapotranspiration (ET), water

Each subpackage contains modules and classes tailored to its domain, with a clear separation of concerns.
For example,  hetao_ag.soil  might include  moisture.py ,  salinity.py , and  sensors.py  for
different  aspects  of  soil  analysis,  while  hetao_ag.livestock  could  have  vision.py  (for  image
analysis) and behavior.py  (for time-series sensor data analysis). This structure makes it easy to maintain
and deploy on diverse platforms – from lightweight edge devices (Raspberry Pi, NVIDIA Jetson) to cloud
servers – by including only the necessary modules in a given application.

return self._to_si
class Quantity:
"""Physical quantity with a value and unit, supporting conversions and 
arithmetic."""
__slots__ = ("value", "unit")
def __init__(self, value: float, unit: Unit):
self.value = value
self.unit = unit
def to(self, target_unit: Unit) -> "Quantity":
# Convert self to target_unit
si_value = self.value * self.unit.to_si_factor
# convert current 
value to SI base
new_value = si_value / target_unit.to_si_factor
# convert SI value 
to target unit
return Quantity(new_value, target_unit)
def __add__(self, other: "Quantity") -> "Quantity":
if not isinstance(other, Quantity):
raise TypeError("Can only add Quantity to Quantity")
si_sum = (self.value * self.unit.to_si_factor) + (other.value *
other.unit.to_si_factor)
return Quantity(si_sum / self.unit.to_si_factor, self.unit)
# (Similar implementations for __sub__, __mul__, etc., ensuring unit 
consistency)
In this snippet, Quantity  objects automatically handle unit conversion. For example, adding 100 centimeters to
2 meters will internally convert both to SI units (meters) and return 3.0 m. This design decision ensures that all
modules operate with consistent units, reducing errors and simplifying collaboration.

hetao.soil – Soil Moisture and Salinity Modeling
Purpose: The  hetao.soil  module models soil hydrology and salinity dynamics – critical for irrigation
management in the Hetao region. It also provides tools to calibrate soil sensors, bridging the gap between
raw IoT sensor readings and scientifically meaningful values. The module is useful in academic research
(e.g., simulating soil moisture under different irrigation schemes) and practical farming (e.g., real-time
sensor calibration and alerts).
Features & Components:
Soil Moisture Modeling: Functions and classes to simulate soil moisture over time. This might
include a simple bucket model for soil water balance or more advanced layers (e.g., a two-layer
model for topsoil vs subsoil moisture). Key processes like infiltration, percolation, evaporation, and
root water uptake are represented. For accuracy, classical models can be incorporated – e.g., using
van  Genuchten  soil  retention  curves  or  Green-Ampt  infiltration  for  certain  studies  –  all  using
standard formulas and parameters from literature.
Soil  Salinity  Modeling: Tools  to  track  salinity  (typically  measured  as  electrical  conductivity  of
saturated paste, ECe, in dS/m). As irrigation water and fertilizers add salts to the soil, this module can
estimate salinity buildup and leaching. It follows internationally recognized approaches, such as the
Mass Balance of salts in the soil profile. For example, if  I  is irrigation water (with certain salt
concentration) and  D  is drainage, the salt balance can be updated each time step. The module

IoT Sensor Calibration: Support for calibrating low-cost soil moisture sensors (capacitive or resistive

specific  response,  so  calibration  functions  (linear  regression,  polynomial  fits,  or  even  machine

formula. This is vital because studies show that with proper calibration, cheap sensors can yield
reliable soil moisture readings
.
Sensor Integration Utilities: Utilities for reading from sensors on devices like Raspberry Pi (e.g.,
using ADC interfaces or I2C for digital sensors) and converting raw signals to moisture percentage or
conductivity. These low-level interactions are abstracted so researchers can replay recorded sensor
data or simulate sensors in a notebook, while field deployments can subclass these utilities to
connect to actual hardware.

hetao.water – Evapotranspiration, Water Balance, and Irrigation
Purpose: The  hetao.water  module  focuses  on  the  water  cycle in  agriculture:  calculating
evapotranspiration (ET), managing water balances (how soil moisture changes due to inputs and outputs),
and helping schedule irrigation optimally. It bridges climate data, soil conditions, and irrigation actions to
ensure crops get enough water without waste, a crucial need in the arid-semiarid Hetao region.
Features & Components:
Reference  Evapotranspiration  (ET<sub>0</sub>)  Calculation: 
The  module  provides
implementations  of  standard  evapotranspiration  formulas.  Chief  among  them  is  the  FAO-56
Penman–Monteith equation, the international standard for computing reference ET<sub>0</sub>
(for a reference crop like grass)
. This formula requires inputs like solar radiation, temperature,
humidity, and wind speed, and yields daily (or hourly) ET. The library also includes simpler empirical
equations (Hargreaves, Thornthwaite, etc.) for cases where data is limited
. By following FAO
guidelines, researchers and practitioners ensure their ET estimates are globally comparable and
scientifically sound.
Crop Evapotranspiration: Functions to derive actual crop ET from reference ET. This typically uses
crop-specific coefficients (K<sub>c</sub> values) as per FAO. The module might include a small
database of K<sub>c</sub> for common crops and growth stages, or allow the  hetao.crop
module to supply dynamic K<sub>c</sub> based on simulated phenology.
Soil Water Balance Model: While hetao.soil  handles soil moisture, hetao.water  can provide
higher-level  water  balance  accounting.  For  example,  a  WaterBalance  class  might  track
precipitation, irrigation, runoff, deep percolation, and ET over time for a field or farm. It ensures that
all inflows and outflows of water are recorded, helping in irrigation scheduling and in analyzing
scenarios (e.g., how much irrigation is needed if next week’s forecast ET is high).

# hetao/water/evapotranspiration.py

def eto_fao56(t_mean: float, t_max: float, t_min: float, rh: float, u2: float,
rs: float,
elevation: float, lat: float, doy: int) -> float:
"""
    Compute daily reference evapotranspiration (ET0) using FAO-56 Penman-
Monteith.
    Inputs:
      t_mean (°C), t_max (°C), t_min (°C) – temperatures,
      rh (%) – mean relative humidity,
      u2 (m/s) – wind speed at 2m,
      rs (MJ/m2/day) – incoming solar radiation,
      elevation (m), latitude (deg), day-of-year.
    Returns: ET0 in mm/day.
    """
# Constants
Gsc = 0.0820
# solar constant (MJ/m2/min)
# Saturation vapor pressure (Tetens formula)
es_tmax = 0.6108 * math.exp(17.27 * t_max / (t_max + 237.3))
es_tmin = 0.6108 * math.exp(17.27 * t_min / (t_min + 237.3))
es = (es_tmax + es_tmin) / 2.0
# mean sat vapor pressure
ea = es * rh / 100.0
# actual vapor pressure
# Slope of vapor pressure curve (kPa/°C)
delta = 4098 * (0.6108 * math.exp(17.27 * t_mean / (t_mean + 237.3))) /
((t_mean + 237.3)**2)
# Atmospheric pressure and psychrometric constant
p = 101.3 * (((293 - 0.0065 * elevation) / 293) ** 5.26)
gamma = 0.000665 * p
# Extraterrestrial radiation for day (from latitude & doy) – simplified:
dr = 1 + 0.033 * math.cos(2 * math.pi / 365 * doy)
delta_sol = 0.409 * math.sin(2 * math.pi / 365 * doy - 1.39)
omega = math.acos(-math.tan(math.radians(lat)) * math.tan(delta_sol))
ra = (24*60/math.pi) * Gsc * dr * (omega *
math.sin(math.radians(lat))*math.sin(delta_sol) +
math.cos(math.radians(lat))*math.cos(delta_sol)*math.sin(omega))
# Net radiation (simplified using rs and clear-sky approx)
rso = (0.75 + 2e-5 * elevation) * ra
# Net shortwave radiation:
rns = 0.77 * rs
# assuming albedo of 0.23, net = (1-0.23)*Rs
# Net longwave radiation:
rnl = (4.903e-9 * ((t_max+273.16)**4 + (t_min+273.16)**4)/2 *
(0.34 - 0.14 * math.sqrt(ea)) * (1.35 * rs/rso - 0.35))
rn = rns - rnl
# net radiation (MJ/m2/day)
# Convert net radiation to equivalent evaporation in mm/day:
# 1 MJ/m2 = 0.408 mm of water
ET0 = (0.408 * delta * (rn) + gamma * (900/(t_mean+273)) * u2 * (es - ea)) /
9
(delta + gamma * (1 + 0.34 * u2))
return ET0
This code computes daily reference ET<sub>0</sub> using the FAO-56 Penman–Monteith equation
. It carefully
follows the international standard, including intermediate steps like net longwave radiation. By exposing such a
function, the library lets users either directly compute ET or verify their data pipeline against a known-good
implementation. Expert users can compare this with other methods (Hargreaves, Thornthwaite) for sensitivity
analysis.

def recommend_irrigation(soil_model, trigger_moisture: float, max_amount_mm:

    Simple rule-based recommendation: 
    If soil moisture falls below trigger_moisture, recommend irrigation up to

    """

# current volumetric moisture 
(fraction)

# Calculate deficit to field capacity
deficit = soil_model.field_capacity - current_moisture
# Convert deficit to depth (mm) over root zone

# m3/m3 * m * 1000 -> 
mm

return apply_mm
# how many mm to irrigate
else:
return 0.0

hetao.crop – Crop Growth and Stress Simulation
Purpose: The hetao.crop  module simulates crop growth and development, incorporating environmental
stresses such as salinity and water deficit. It enables researchers to model “what-if” scenarios (e.g., how a
maize yield changes under saline irrigation) and helps agronomists predict yields and plan management.
The module aligns with international crop modeling practices, ensuring that models use standard growth
stages, units, and stress-response functions so results can be validated against literature.
6
10
Features & Components:
Phenology and Growth Modeling: Representations of crop growth stages (emergence, vegetative,
flowering, grain fill, maturity, etc.) either through thermal time (growing degree days) or calendar
days. The module may include a CropModel  base class with parameters like max leaf area index
(LAI), light use efficiency, harvest index, etc. Growth of biomass can be simulated as a function of
intercepted light (possibly using the radiation data from  hetao.water ) and transpiration. The
structure takes inspiration from well-known models (e.g., AquaCrop, DSSAT, APSIM) but is adapted
for simplicity and custom research needs.
Water Stress Response: When soil moisture is below optimal, crops experience stress that reduces
transpiration and growth. hetao.crop  works closely with hetao.soil  and hetao.water  to
obtain  the  actual  transpiration.  It  then  computes  a  water  stress  coefficient (often  denoted
K<sub>s</sub>) which reduces growth or yield. For example, if only 70% of water demand was met,
certain models assume proportional biomass reduction.
Salinity  Stress  Response: High  soil  salinity  can  significantly  reduce  crop  yield.  The  library
implements standard salt tolerance models. A common approach is the  threshold-slope model
(Maas & Hoffman): each crop has an ECe threshold below which yield is 100%, and beyond that
threshold, yield declines linearly with slope (% yield loss per dS/m)
. For instance, if wheat has
threshold 6 dS/m and slope 7% per dS/m, and the field ECe is 8 dS/m, expected yield is about 86% of
potential.  More  advanced,  the  module  could  also  include  nonlinear  response  curves  (e.g.,  van
Genuchten’s sigmoid model for salt stress
). These functions allow simulation of scenarios like
using brackish water for irrigation and quantifying the impact on crop output.
Yield Prediction: Combining growth simulation and stress factors, the module can estimate final
yield. This could be done via harvest index (fraction of biomass that becomes yield) adjusted by
stress, or through direct empirical models per crop. Internationally recognized parameters (from
FAO or USDA databases) can be included for default crop profiles, so users have a starting point for
major crops.
Management Factors: The module can take into account planting density, fertilization (perhaps in a
simplified way), and other factors that might influence growth, to allow holistic experimentation.
However, core focus remains water and salt, as per the Hetao region’s priorities.

Example – Salinity Stress Yield Reduction (Snippet):
# hetao/crop/stress.py
def yield_reduction_salinity(ECe: float, threshold: float, slope: float) ->
float:
"""
    Compute relative yield (0-1) given soil salinity (ECe, dS/m) using a 
threshold-slope linear model.
    - threshold: ECe (dS/m) below which yield is full (no reduction).
    - slope: yield reduction per 1 dS/m increase in salinity beyond threshold 
(fraction per unit).
    """
if ECe <= threshold:
return 1.0
# no yield loss
# yield declines linearly beyond threshold
# e.g., if slope = 0.1 (10% per dS/m) and ECe is 2 above threshold, 
reduction = 0.2 (20%)
reduction_fraction = slope * (ECe - threshold)
rel_yield = 1.0 - reduction_fraction
# yield cannot be less than zero
return max(0.0, rel_yield)
# Example usage:
wheat_threshold = 6.0
# dS/m, example value

def compute_ndvi(red_band: np.ndarray, nir_band: np.ndarray) -> np.ndarray:

denominator = nir + red

Integration into Research Workflows
Designing hetao_ag  for expert users means ensuring it fits seamlessly into research and development
workflows.  Key  considerations  include  reproducibility,  configurability,  collaboration,  and  the  ability  to
validate and communicate results. Below are guidelines and features that facilitate integration:
Reproducible Experiments: All modules are designed to allow deterministic behavior given the
same inputs. By using the hetao.core.ConfigManager , researchers can save all parameters of a
simulation or analysis to a config file and later reload it to exactly reproduce the run. We also
encourage  capturing  random  seeds  for  any  stochastic  processes  (e.g.,  in  hetao.opt  genetic
algorithms) in the config or logs to allow repeatability
. The library’s logging (in core.Logger )
can automatically record the configuration and seed at the start of each run for traceability.
Configuration-Driven Workflow: Researchers can set up complex simulations by writing a YAML/
JSON  config  specifying,  for  example,  which  crops  to  simulate,  what  sensors  to  calibrate,  what
optimization to run, etc. A high-level script can then load this config and invoke the appropriate
hetao_ag  modules. This separates code from parameters, which is a best practice for scientific
workflows
. For instance, a config might define multiple scenarios (different irrigation strategies);
a simple loop in a Python script can iterate over these scenarios and produce comparative results, all
while the core logic remains unchanged.
Jupyter Notebook Friendly: The library is built to play well in interactive environments. Clear,
concise APIs and reasonable default behaviors mean users can prototype analyses in notebooks
quickly (e.g., compute NDVI from an image, then apply a crop model) without needing boilerplate.
Additionally, results (like index maps or optimization outcomes) can be easily converted to Pandas
DataFrames, NumPy arrays, or visual plots, which is essential for quick visualization in research. For
example, the output of an optimization can be visualized as a bar chart of land allocation; the NDVI
time  series  can  be  plotted  to  show  crop  growth  curves.  By  making  such  data  retrieval
straightforward, we ensure researchers spend more time on insight and less on format wrangling.
Interoperability:
hetao_ag  follows standard data structures (e.g., using NumPy arrays, Pandas
DataFrames, GeoTIFF files) so that it can be combined with other scientific libraries. Researchers
might use SciPy or statsmodels to further analyze outputs, or use matplotlib/seaborn for custom
plots. Because we adhere to those standard formats, they can do so without friction. For example, a
user can take a WaterBalance  time series from our module (perhaps as a Pandas Series of soil
moisture over time) and directly apply statistical analysis or export it to CSV.
Documentation and Examples: The library will include comprehensive English documentation, with
examples for common tasks. This might be in the form of a Sphinx-generated site or Jupyter
notebooks demonstrating typical workflows (sensor calibration, running a crop model for a season,
optimizing crop mix, etc.). Clear documentation lowers the entry barrier for new researchers and
ensures that even expert users don’t waste time deciphering APIs. Each module’s functions and
classes are documented with docstrings (PEP 257 compliant), possibly including references to the
underlying scientific methods (e.g., citing FAO papers for ET, or relevant journal articles for a model).
This not only helps in usage but also in academic writing – users can trace how a result was obtained
and cite the proper sources.

demands incremental modifications, the code repository (if shared among a team) should be under
version control (Git). Researchers can develop new features or tweak models on branches, run tests,

Publishing and Collaboration: When it comes time to publish findings or share with stakeholders,

and repeatability

Best Practices for Deployment (Edge and Cloud)
The hetao_ag  library is intended to run in a variety of environments – from a Jetson Xavier monitoring a
barn in real-time, to a cloud server crunching years of satellite data. Deployment best practices ensure the
library performs optimally and reliably in each scenario:
1. Lightweight Deployment on Edge Devices (Raspberry Pi, NVIDIA Jetson):
Modular Installation: Edge devices often have limited storage and performance. We suggest a
modular installation where only needed submodules (and their dependencies) are installed on the
device. For instance, a Raspberry Pi running irrigation control might only need core , soil , and
water  (and not the heavy CV or remote sensing libraries). The library can be packaged such that
optional dependencies (like OpenCV, torch, rasterio) are only installed when their module is used.
This keeps the footprint small.
Optimized Libraries: On NVIDIA Jetson, leverage NVIDIA’s optimized libraries. For computer vision,
this means using CUDA acceleration and TensorRT. The hetao.livestock  module, as noted, will
try to load models in half precision on GPU. We recommend building OpenCV with CUDA for Jetson
and using NVIDIA’s Vision Programming Interface (VPI) where possible
. For example, image
processing (like resizing or color space conversion) can use VPI or OpenCV’s cv2.cuda  methods to
exploit the GPU. Similarly, linear algebra in numpy can benefit from BLAS libraries tuned for ARM.
Ensuring  these  are  in  place  (perhaps  via  JetPack  on  Jetson,  which  includes  cuDNN,  etc.)  will
significantly speed up computations.
Performance and Power Management: Edge devices can have variable performance modes. On
Jetson,  running  in  MAXN  mode  (full  power)  and  enabling  all  CPU/GPU  clocks  is  important  for
demanding tasks
. We suggest documentation or utilities in hetao_ag  that check for Jetson
and  remind  the  user  to  enable  these  modes  (with  commands  like  nvpmodel  and
jetson_clocks )
. Additionally, monitoring tools such as tegrastats  can be integrated (or at
least referenced) to continuously watch resource usage
. The library could include an optional
PerformanceMonitor  that logs CPU/GPU usage and memory, so one can ensure the code stays
within safe limits (preventing overheating or memory exhaustion).
Containerization on Edge: Using Docker containers on devices like Jetson Nano is a best practice
for consistent deployment
. We recommend deploying hetao_ag  within a Docker that contains
all required dependencies (especially for CV and ML which can be tricky to set up). The library will
provide a reference Dockerfile for Jetson (arm64) and Pi. It will base on NVIDIA’s L4T base image (for
Jetson) so it can use GPU acceleration. Inside, it will install  hetao_ag  and any needed system
packages (e.g., libgdal  for space module). By containerizing, we ensure that the field deployment
runs the exact same stack as tested. It also simplifies updates – e.g., a new version of the library can
be deployed by just swapping the container image, which supports OTA updates in the field
.
Robustness  and  Fault  Tolerance: Edge  deployments  must  be  resilient  to  intermittent  issues
(network drops, sensor glitch). The library’s design encourages exception handling and failsafes. For
example, if a sensor read fails,  hetao.soil  could return the last known value or a NaN that
higher-level code can catch and handle (like skipping an irrigation cycle rather than crashing).

2. Scalable Deployment in Cloud or Server Environments:
Parallel and Distributed Computing: Some tasks, like processing satellite imagery for an entire
region or running many crop model simulations (e.g., a Monte Carlo for climate scenarios), are heavy
and suited for cloud. The library should be usable in parallel workflows. We ensure that our code
releases the GIL where possible (heavy computations in numpy release GIL, or we can use numba for
certain loops). For embarrassingly parallel tasks, we encourage using Python’s multiprocessing
or joblib. For instance, if simulating 100 fields independently, a user can spawn multiple processes
each  using  hetao.crop  on  a  subset.  The  library’s  stateless  design  (each  model  instance  is
independent) makes this safe. On a cluster or cloud, one might use Dask or Spark; as long as
hetao_ag  functions  operate  on  data  passed  in  and  out,  they  can  be  wrapped  into  such
frameworks. We’ll provide examples for running large batch simulations using multiprocessing
for those not familiar.
Cloud Services Integration: For cloud-based deployment, integration with data services is key.
hetao.space  can be configured to fetch data from cloud object storage or APIs. For example,
instead of reading a local file, ImageLoader  could accept an S3 URL or a Google Cloud Storage
path (assuming credentials available). Using libraries like requests  or cloud SDKs, we can stream
data directly without manual download. Similarly, results could be stored to cloud databases or
message queues. While the library doesn’t hardcode any cloud platform, it remains flexible. For
instance, we might provide an interface DataStore  that can be implemented for local filesystem
or cloud storage; the user chooses and passes it to functions that need to load/save files.
Microservices and APIs: In a production cloud scenario, one might deploy parts of the library
behind web services. For example, a Flask or FastAPI app could use  hetao_ag  to provide an
endpoint “upload your farm data and get an optimized irrigation schedule.” Our stateless function
design and clear input-output make this straightforward. The best practice here is to ensure thread
safety: since some web frameworks use multi-threading, our library functions avoid global state. We
either encapsulate state in objects or use functional approaches. Additionally, heavy initialization
(like  loading  a  deep  learning  model)  is  done  once  (e.g.,  at  service  startup,  instantiate
AnimalDetector ) and reused, rather than loading models on every request. This is demonstrated
in our design by making model loading explicit (e.g., the AnimalDetector  class loads the model in
__init__ , so an API can keep a global instance of it).
Continuous Integration/Deployment (CI/CD): For cloud or even edge (with containers), it’s good
practice to automate testing and deployment. We suggest maintaining a CI pipeline that runs the
test suite on each commit (to catch regressions). Since the library might run on ARM (edge) and x86
(cloud), testing on both architectures or using emulators in CI is beneficial. For deployment, if using
Docker, a CI can build the images and push to a registry. Developers at Hetao College could then pull
the updated image to devices. The key point is that the library’s thorough testing and modular

Security and Access: In cloud, one must secure the system. Although  hetao_ag  mainly does

3. Field Deployment Considerations:
Environment Hardening: The library should handle irregular conditions in the field gracefully. For
example, in extreme cold or hot, sensor values might be out of normal range – our calibration
functions and models should not crash on unexpected values but perhaps clip them with warnings.
Similarly, if GPS or remote sensing data is temporarily unavailable, the system might continue with
last known good state. By designing components to be robust (using try/except, checks for None or
nan values), we prevent a single faulty reading from bringing down the whole pipeline.
Remote Monitoring and Logging: For devices deployed remotely (common in agriculture), being
able to monitor them from afar is critical. While not inherently part of hetao_ag , we encourage
using its logging output in conjunction with remote logging services. For instance, pushing logs to a
cloud server or at least keeping them accessible via an IoT hub. The library’s consistent log format
means one can write small forwarding scripts or use existing IoT frameworks to ship logs. If
something fails on an edge node, the logs (or even alerts triggered by exceptions) can inform the
team immediately. We could integrate a simple feature: if  ConfigManager  has a setting for a
webhook or MQTT topic for errors, the Logger  could publish critical errors there. This way, an out-
of-the-box deployment can notify maintainers of problems (like “moisture sensor calibration needed”
or “camera feed lost”).
OTA  Updates: Following  best  practices,  we  advocate  for  mechanisms  to  update  the  library  or
application code remotely
. By using containers or package managers, one can push updates
without physical access. We would maintain semantic versioning for hetao_ag  so that users know
if an update is major (possibly breaking) or minor (additive, safe). Devices should ideally pin to a
version that’s tested in their context, and update after validating new versions. We mention this in
docs to ensure users in deployment think about version management (perhaps staging updates on a
test device before rolling out widely).
International Standards & Compliance: Since the library follows international units and methods,
it inherently eases compliance with any regional reporting requirements. For example, water usage
could be reported in cubic meters (standard) and easily converted to the local unit if needed by using
the unit system. If deploying in contexts that require ISO standards for data interchange (like ISO
19156 for sensor data, or agro-meteorological data standards), being consistent with units and open
